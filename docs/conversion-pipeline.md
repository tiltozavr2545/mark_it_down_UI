# Конвейер: файл → Markdown

Главный документ проекта. Здесь — путь, который проходят байты от момента,
когда файл попал в приложение, до строки в буфере обмена, и контракты, на
которые опираются все конвертеры.

Отдельно от [client-architecture.md](client-architecture.md), потому что это не
про Flutter: конвейер — чистый Dart, без единого импорта `flutter/`, и он
обязан собираться и тестироваться как обычная консольная библиотека. Это не
вкусовщина, а условие: конвертацию надо гонять в изоляте и в CI без эмулятора.

Что по каждому конкретному формату решено и чем закрыто —
[format-coverage.md](format-coverage.md). Чем это отличается от настоящего
markitdown — [python-sidecar.md](python-sidecar.md).

---

## Откуда взяты контракты

Интерфейс повторяет markitdown сознательно и близко к буквальному:
`StreamInfo`, `accepts()`/`convert()`, числовые приоритеты конвертеров, единый
объект результата. Причина простая: **нам нужно сверять свой вывод с её
выводом** на одних и тех же файлах, и чем ближе устройство, тем дешевле
разбираться, почему вывод разошёлся. Заодно это позволяет на десктопе
подставить настоящий markitdown за тем же интерфейсом — как ещё один
конвертер, см. ниже.

Там, где мы от неё отходим, это отмечено прямо в тексте.

## Этапы

```
источник (picker / drag&drop / share / clipboard)
   ↓  байты + имя файла + mime от ОС (которому нельзя верить)
[1] распознавание типа         → StreamInfo
   ↓
[2] выбор конвертера           → реестр, accepts() по возрастанию приоритета
   ↓
[3] конвертация в изоляте      → ConversionResult | ConversionFailure
   ↓
[4] предпросмотр               → сырой Markdown
   ↓
[5] буфер обмена / файл .md
```

Границы между этапами — не украшение: 1–3 не знают про UI, 4–5 не знают про
форматы. Единственное, что их связывает, — `ConversionResult`.

## [1] Распознавание типа

`StreamInfo` — то, что известно о потоке до его разбора. Поля те же, что в
markitdown:

| поле | откуда | насколько можно верить |
|---|---|---|
| `filename` | от источника | имя может быть любым |
| `extension` | из `filename` | **врёт регулярно** |
| `mimeType` | от ОС (share/picker) | на Android часто `application/octet-stream` |
| `charset` | определяется для текстовых | отсутствует у бинарных |
| `localPath` | если файл лежит на диске (диалог, drag&drop) | нужен сайдкару, см. ниже; Dart-конвертеры его не читают |

Порядок определения — от дешёвого к дорогому, и первый уверенный ответ
побеждает:

1. **Магические байты.** Первые несколько килобайт: `PK\x03\x04` → zip-семья,
   `%PDF-` → PDF, `\xD0\xCF\x11\xE0\xA1\xB1\x1A\xE1` → OLE2
   (`.doc`/`.xls`/`.msg`/`.ppt`), сигнатуры картинок. Дёшево и надёжнее
   расширения.
2. **Уточнение внутри контейнера.** `PK` сам по себе не говорит ничего: `docx`,
   `xlsx`, `pptx`, `epub`, `apk` и обычный архив — всё это zip. Различаются по
   содержимому: `[Content_Types].xml` (OOXML, дальше по типу части),
   `mimetype` первым файлом (EPUB), иначе — обычный архив. То же с OLE2: все
   его форматы делят одну сигнатуру, и различает их каталог Compound File
   (`type_detection/ole2_directory.dart` — минимальный разбор, только имена
   записей, без сторонних пакетов): `Workbook`/`Book` → `xls`,
   `__properties_version1.0` или `__substg1.0_*` → `msg`, `WordDocument` →
   `doc`, `PowerPoint Document` → `ppt`. Каталог не прочитался (обрезанный
   файл, нестандартный контейнер) — остаётся «OLE2-контейнер» с подсказкой по
   расширению.
3. **Расширение** — только как подсказка, когда байты неоднозначны (`.csv`
   против `.tsv`, `.md` против `.txt`).
4. **Кодировка** для текстовых: BOM, затем эвристика. Текст без BOM, который
   не разбирается как UTF-8, — не «битый файл», а, скорее всего, Windows-1251;
   на русскоязычных выгрузках это обычное дело.

markitdown на этом шаге использует `magika` — ONNX-модель Google. Мы её не
берём: это ~1 МБ модель и рантайм в бандле ради задачи, которую на нашем
наборе форматов закрывают сигнатуры. **Если** набор расширится до форматов,
которые сигнатурами не различить, решение стоит пересмотреть — но тогда
осознанно и с замером.

## [2] Реестр конвертеров

```dart
abstract interface class DocumentConverter {
  String get id;                       // 'docx', 'html', 'sidecar'
  double get priority;                 // меньше — спрашивается раньше
  bool accepts(StreamInfo info, Uint8List head);
  Future<ConversionResult> convert(ConversionRequest request);
}
```

Реестр хранит конвертеры, отсортированные по `priority`, и отдаёт файл первому,
чей `accepts()` сказал «да». Приоритеты — как в markitdown:

- **0.0 — конкретный формат.** `docx`, `pdf`, `xlsx`: конвертер знает, что
  именно перед ним.
- **10.0 — общий формат.** `html` и `plain text`: они возьмут что угодно
  текстовое, поэтому спрашиваются последними. Иначе `html`-конвертер
  перехватил бы `.docx`, из которого торчит XML.

`accepts()` получает `head` — уже прочитанные первые байты, а не поток: иначе
каждый конвертер в цепочке начинал бы читать файл с начала, и на мобильном
файле в сотню мегабайт это бы стоило заметно.

**Отличие от markitdown:** у нас `accepts()` синхронный и не имеет права
трогать диск. Решение «мой ли это файл» принимается по `StreamInfo` и `head`;
всё, что требует разбора, — уже внутри `convert()`. Так цепочка перебора
остаётся предсказуемо быстрой.

### Сайдкар — просто ещё один конвертер

На десктопе в реестр добавляется `SidecarConverter` с приоритетом **-1.0** для
форматов, перечисленных в его манифесте, — то есть он спрашивается раньше
Dart-конвертеров там, где настоящий markitdown заведомо лучше, и не мешает
там, где нет. Приложение выше реестра про сайдкар не знает вообще; на
мобильных он просто не регистрируется.

Единственное, что протекает наружу: сайдкару нужен **файл на диске**
(`localPath`), а не байты в памяти — он получает путь аргументом. Если у
файла есть `StreamInfo.localPath` (диалог, drag&drop), передаётся он; для
данных без пути (буфер обмена, вложенный файл архива) `SidecarConverter`
пишет байты во временную папку с расширением по id формата и удаляет её в
`finally`. Удалять обязан вызывающий (конвертер), а не сайдкар — иначе
непонятно, кто владеет; чужой файл по `localPath` не удаляется никогда.

**Какие форматы берёт.** Только перечисленные в `manifest.json` и известные
приложению (`pdf`, `docx`, `xlsx`, `xls`, `pptx`, `msg`; сопоставление
`FileKind` ↔ id — в `sidecar_manifest.dart`). `xls`/`msg` распознаются по
каталогу OLE2 (см. выше) и **существуют только через сайдкар**: Dart-
конвертеров для них нет, на мобильных они остаются «не поддерживается» —
осознанное решение плана. Манифест битый или с неизвестной `schema` —
сайдкар не регистрируется, приложение не падает.

**В приложении — только `pdf`/`xls`/`msg`, PDF — до 50 страниц** (решение
автора, Этап 5, п. 5). `discover()` сужает манифест до
`SidecarConverter.appFormats` и задаёт `maxPdfPages = appMaxPdfPages`:
сайдкар в десятки раз медленнее Dart, а в `docx`/`xlsx`/`pptx` Dart по сверке
не хуже, так что первым сайдкар идёт только там, где даёт недостающее, —
`xls`/`msg` и таблицы в PDF. PDF длиннее порога сайдкар отклоняет, не
запуская Python (`countPdfPages` через PDFium — дерево страниц, без
разбора текста), реестр отдаёт файл Dart-конвертеру, а в `warnings`
пишется, что таблицы извлечены как текст. `fromDirectory()` без
`onlyFormats` видит весь манифест — так сайдкар остаётся эталоном для
`make compare-sidecar` и интеграционных тестов.

**Где ищется.** `SidecarConverter.discover()`: на Android/iOS всегда `null`;
на десктопе — `MARKITDOWN_SIDECAR_DIR` (разработка и тесты, по образцу
`MARKITDOWN_PDFIUM_PATH`; если задана, другие места не смотрятся), иначе на
macOS `Contents/Resources/sidecar` рядом с исполняемым файлом бандла, на
Windows — `sidecar\` в каталоге `.exe` (туда его кладёт
`install(DIRECTORY …)` в `app/windows/CMakeLists.txt`). Нет
каталога — просто не регистрируется. Поиск идёт внутри изолята конвертации
(`isolated_convert.dart`), конвертер между изолятами не пересылается.

**Подмена в тестах.** Команда запуска собирается в одном месте —
`SidecarCommandBuilder` (путь входного файла + id формата → исполняемый файл
и аргументы). `SidecarConverter.fromDirectory` строит стандартную
(`python/bin/python3 -I -B run.py --in … --format …`, на Windows —
`python/python.exe`); тесты либо кладут в
каталог shell-скрипт вместо интерпретатора, либо передают свой builder
в конструктор.

**Отказ сайдкара — откат на Dart-конвертер.** Реестр отдаёт файл первому
подошедшему конвертеру, и обычно его отказ окончателен. Сайдкар — исключение:
любой его провал (код 2, 3, 1, таймаут, невалидный JSON при коде 0, не
запустился, вывод больше предела) бросает `ConversionDeclinedException`, и
реестр идёт к следующему конвертеру, чей `accepts()` тоже сказал «да», то есть
к Dart-реализации того же формата (`pdf`, `docx`, `xlsx`, `pptx`). Почему:
сайдкар — усиление поверх Dart-ядра, а не его замена; зависший или упавший
подпроцесс не должен отнимать результат, который ядро отдаёт само («частичный
результат полезнее отказа»). Это верно и для кода 3: `pdfminer` строже
PDFium, а по-настоящему битый файл Dart-конвертер всё равно отвергнет — со
своим, обычно более точным, описанием места. Если запасной справился, к
`warnings` первой строкой добавляется «сайдкар не смог обработать файл
(причина)», чтобы расхождение с эталоном не было загадкой. Если запасного нет
(`xls`/`msg`) или он тоже провалился, пользователь получает отказ, описанный
в «Ошибках» ниже.

## [3] Конвертация

```dart
class ConversionRequest {
  final Uint8List bytes;
  final StreamInfo info;
  final ConversionLimits limits;
  final Future<ConversionResult> Function(ConversionRequest) recurse;
}

class ConversionResult {
  final String markdown;
  final String? title;            // из метаданных документа, если есть
  final List<ConversionWarning> warnings;
  final String converterId;
  final Duration elapsed;
}
```

`recurse` в запросе — не украшение: `zip` и `epub` обязаны прогнать вложенные
файлы через тот же реестр, и сделать это, не импортируя реестр напрямую,
иначе получается цикл зависимостей. Вместе с этим идёт жёсткое правило:
**рекурсия ограничена глубиной и общим числом файлов** (`ConversionLimits`).
Zip, который содержит себя, — не теоретический случай, а известный способ
уронить любой распаковщик.

`warnings` — отдельный список, а не исключение, потому что **частичный
результат полезнее отказа**. PDF, в котором половина страниц — сканы, должен
отдать текст с остальных и честно сказать, чего не хватает. Отказ целиком
допустим только когда отдавать нечего.

Конвертация запускается в изоляте (`Isolate.run`). Причина не в вежливости к
UI, а в том, что разбор 50-мегабайтного `xlsx` — это секунды сплошного CPU, и
на главном изоляте он замораживает окно вместе с анимацией прогресса.
Следствия этого выбора — в
[client-architecture.md](client-architecture.md#конвертация-в-изоляте).

## Как Markdown собирается

Решения о представлении — то, ради чего мы вообще смотрим на markitdown.
Общие для всех конвертеров:

- **Вывод — текст для человека и для LLM**, а не точная копия документа.
  Оформление, которое не несёт смысла (цвета, шрифты, выравнивание), теряется
  намеренно.
- **Структура сохраняется заголовками.** Уровень заголовка в документе → `#`
  соответствующего уровня; нумерация не дописывается руками.
- **Таблицы — Markdown-таблицами**, пока они прямоугольные. Объединённые
  ячейки Markdown не выражает: такая таблица отдаётся HTML-блоком, и это
  фиксируется в `warnings`. Молча ломать сетку хуже, чем отдать HTML.
- **Изображения внутри документов становятся ссылками-заглушками**
  `![alt](имя-файла)`, а не base64. Base64-картинка в промпте — это десятки
  тысяч токенов мусора ради того, чего модель всё равно не увидит.
- **Текст не переносится по ширине.** Жёсткие переносы ломают вставку в
  редакторы, которые сами заворачивают абзац.
- **Экранирование.** Символы, которые в исходном тексте значат себя (`*`, `_`,
  `#`, `|`, `` ` ``), экранируются; это самый частый источник «а почему тут
  поехало форматирование».

Эти правила живут **одним модулем** (`markdown_writer`), а не повторяются в
каждом конвертере. Повод отдельный: в Amicus правило видимости разошлось по
четырём копиям, две из которых отстали и стали дырами, — та же ошибка здесь
даёт конвертеры, которые по-разному экранируют один и тот же символ.

## Ошибки

Отказ — тоже результат, и он обязан быть понятным: «не удалось прочитать
файл» — это не сообщение. Разделяются три случая, и у них разные тексты и
разные действия в UI:

| случай | пример | что показываем |
|---|---|---|
| формат не поддерживается | `.sketch` | какой это формат и что поддерживается |
| формат поддерживается, файл битый | обрезанный zip | что файл повреждён, на каком месте |
| превышен лимит | файл 2 ГБ, 10 000 файлов в архиве | какой именно лимит и какой он |

Сырой текст исключения пользователю не показывается никогда — в Amicus это
закрывали отдельным багфиксом уже после релиза, здесь закладывается сразу.

Сайдкар укладывается в те же три случая, а его stderr не показывается
вообще — он лежит только в `ConversionDeclinedException.diagnostics` для
разработчика:

| сайдкар | случай |
|---|---|
| код 2 | формат не поддерживается |
| код 3 | файл повреждён |
| таймаут (по умолчанию 120 с, процесс убивается `SIGKILL`), вывод больше предела | превышен лимит — «время обработки сайдкаром превысило N с» |
| код 1, любой другой код, не запустился, невалидный JSON при коде 0 | файл повреждён / не удалось обработать (без подробностей) |

Подробности отката на Dart-конвертер — в «Сайдкар — просто ещё один
конвертер» выше.

## [4]–[5] Предпросмотр и буфер

Предпросмотр показывает **сырой Markdown**, не отрендеренный. Пользователь
копирует текст, и видеть он должен текст; отрендеренная версия создавала бы
ровно то расхождение между «что вижу» и «что получу», из-за которого потом
непонятно, кто испортил таблицу.

В буфер кладутся **два представления одновременно**: `text/plain` и
`text/markdown` (на Windows — ещё и `CF_UNICODETEXT`, это тот же plain).
`Clipboard.setData` из `flutter/services` умеет только одно, поэтому берётся
`super_clipboard`. Редакторы, которые понимают `text/markdown`, получают
разметку; все остальные — ровно тот же текст как есть, то есть хуже не
становится никому.

«Сохранить как `.md`» пишет UTF-8 **без BOM** и с `\n` — включая Windows:
BOM и `\r\n` в Markdown-файле ломают больше инструментов, чем исправляют.
